# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

The Smart Send WooCommerce plugin (display name "Smart Send", slug `smart-send-logistics` - the WordPress.org slug can never change). It adds Smart Send shipping methods to WooCommerce, shows carrier pick-up points at checkout, and generates shipping labels via the Smart Send API. Supported carriers: PostNord, GLS, DAO, Burd, Budbee, Bring.

The actual plugin lives entirely in `smart-send-logistics/` — that folder is what gets shipped to the WordPress.org plugin directory. The repo root only holds dev tooling (`composer.json` for phpcs, `bin/svn-deploy.sh`, README).

## Development environment

There is no PHP build step. Development is done against local WordPress + WooCommerce installs created by `bin/setup-local-dev.sh` (shorthand: `composer setup`; plugin symlinked in and activated). Two git-ignored env files at the repo root pin the store locations (`WP_PATH` relative to the repo root + `WP_URL`): `.env` is the persistent dev store (manual testing, demo mode; typically Herd-served at a `*.test` URL), `.env.testing` is the disposable testing store (default `./local-dev/wordpress` at `http://127.0.0.1:8181`, matching CI) that `bin/run-tests.sh` rebuilds from scratch on every `composer test:*` run. Explicit `--path`/`--url` flags and the legacy `WP_DEV_PATH`/`WP_BASE_URL` env vars override the files. The store is seeded to look like a real webshop (for manual testing and documentation screenshots): the vendored sample catalog in `sample-data/` (WooCommerce core sample products enriched to kg/cm and DKK, images committed for offline determinism — refresh via `bin/update-sample-data.sh`, never edit by hand), a Storefront homepage + primary menu, and default onboarding/marketing admin notices suppressed. The README.md has further details on the development environment.

### JS build

Two compiled assets: the checkout-block scripts (`src/pickup-point-block/` → `build/pickup-point-block/`) and the order screen meta box app (`src/order-fulfillment/` → `build/order-fulfillment/`, #182). Source lives in `src/` at the repo root (dev tooling, like `composer.json`); `npm run build` (`@wordpress/scripts`, Node version pinned in `.nvmrc`, config in `webpack.config.js`) compiles it into `smart-send-logistics/build/`, with `@woocommerce/dependency-extraction-webpack-plugin` turning `@wordpress/*`/`@woocommerce/*` imports into externals listed in generated `*.asset.php` files. The meta box app's files opt into the **classic JSX runtime** (`/** @jsxRuntime classic */ /** @jsx createElement */` pragmas + `createElement` from `@wordpress/element`): `@wordpress/scripts` defaults to the automatic runtime, whose `react-jsx-runtime` script handle WordPress registers only from 6.6, so on the 6.5 floor an automatic-runtime bundle silently never loads (#183) — keep the pragmas on every JSX file of that entry (an Integration test pins that `index.asset.php` lists no `react-jsx-runtime`). The `build/` output is **committed** — contributors without Node get a working plugin and `bin/svn-deploy.sh` stays copy-only — and `.github/workflows/js-build.yml` rebuilds on PRs touching `src/`/`package*.json`/`webpack.config.js` and fails if the committed output drifts from `src/`. After changing anything under `src/`, run `npm run build` and commit the result. Generated `build/` files are excluded from phpcs.

## Testing

Three Pest suites live in `tests/` (run on modern PHP; the plugin's PHP 7.4 floor only applies to `smart-send-logistics/` code):

- **Browser** (`tests/Browser`) — end-to-end Playwright tests against a *running* store over HTTP (`WP_BASE_URL`, default `http://127.0.0.1:8181`). Few and slow; cover the big flows. `tests/Browser/DevStoreTest.php` is the baseline health check of the dev store *itself* (Storefront theme active, store-page wiring, cart → checkout navigation, no JS errors) with no Smart Send seeding — when the store misbehaves, run that file first (`vendor/bin/pest tests/Browser/DevStoreTest.php`) before debugging the plugin.
- **Integration** (`tests/Integration`) — WordPress + WooCommerce loaded *in-process* by `tests/bootstrap.php` from the `bin/setup-local-dev.sh` install (override with `WP_DEV_PATH`); no web server needed. This is where scenario coverage lives (orders with coupons, discounts, fees → shipment payload, filters). Fixtures are built via the factories in `tests/Integration/Helpers.php`, which force-delete everything they create after each test — always create test data through them.
- **Docs** (`tests/Docs`) — *not* a correctness suite. Drives Playwright through real admin UI flows (same running store as Browser) and captures named screenshots for documentation, one test per meaningful UI state (see `tests/Docs/ShippingMethod/ConfigureShippingMethodTest.php` for the pattern — configuring a Smart Send shipping method on a zone, step by step; `tests/Docs/OrderFulfillment/OrderMetaBoxTest.php` captures the order meta box states of #182 into `docs/screenshots/OrderFulfillment/`, seeded through the Browser suite's `ss_browser_seed_store()` and API mock). Shared helpers live in `tests/Docs/Support/Screenshots.php`: `capture_doc_screenshot()` (asserts `assertNoJavaScriptErrors()` - not the stricter `assertNoSmoke()`, since WordPress admin always emits at least one benign console log - then saves under `docs/screenshots/<Area>/<name>.png`) and `highlight_element()` (spotlight-outlines the field a screenshot is calling out). Runs **headed** (a visible browser window) by default via `Playwright::headed()` in `tests/Pest.php` (a directory-level `tests/Docs/Pest.php` is never loaded by Pest for nested test files, so this lives at the root instead), so a developer regenerating screenshots locally can watch it work; falls back to headless when the `CI` env var is set (GitHub Actions sets this automatically) or when `SS_DOCS_HEADLESS` is set for a manual opt-out. To watch at human speed, set `SS_DOCS_SLOWMO=<ms>` (e.g. `SS_DOCS_SLOWMO=1500 composer test:docs`) — it pauses at every highlight/screenshot state via `docs_slowmo_pause()`; unset means full speed.

```bash
composer test:integration   # fresh testing store, then the Integration suite
composer test:browser       # fresh testing store + managed web server, then Browser
composer test:docs          # fresh testing store + managed web server; opens a visible browser locally
composer test               # Integration + Browser (not Docs - see below)
```

Every `composer test:*` script goes through `bin/run-tests.sh`: it **rebuilds the testing store (`.env.testing`) from scratch** (`bin/setup-local-dev.sh --env testing --force`) so runs never drift, and starts/stops the store's web server itself when `WP_URL` is a localhost URL. The order storage backend is a setup knob (`--order-storage hpos|posts|default`, or `WP_ORDER_STORAGE` in the env file): the Browser suite's order screen tests read `ss_browser_state()['hpos']` for paths and selectors, so the same files cover the HPOS and the legacy order screen — CI runs one HPOS-off leg (`--order-storage posts`) on the newest PHP next to the default matrix. For quick iteration against the *existing* testing store, call Pest directly (`vendor/bin/pest --testsuite=Integration`, etc.) — for Browser/Docs you then manage the server yourself.

For manual testing there is a demo mode (`composer demo:on` / `demo:off` / `demo:scenario -- <name>`, backed by `bin/demo-store.sh`): it applies the Browser suite's seeded store state + API mock to the local dev store and leaves it on until turned off. The mock and seeding sources are shared with the Browser suite (`tests/Browser/Support/ApiMockMuPlugin.php` + `Snippets/*.php`) — one source of truth; see README "Manual testing (demo mode)".

Local runs are fast: a direct `vendor/bin/pest` suite finishes in under 2 minutes, and a `composer test:*` run adds well under a minute of fresh-store provisioning on top (WP-CLI caches the downloads). If a run takes meaningfully longer, something is wrong (store not reachable, wrong `WP_URL`, a hung Playwright session) — kill it and investigate instead of waiting.

CI runs Integration and Browser (`.github/workflows/browser-tests.yml` and `integration-tests.yml`) on every pull request and on pushes to `main` and `develop`. Each matrix has `latest` legs (every supported PHP version — 7.4 to 8.5 for Browser, Pest's 8.3 to 8.5 for Integration — on the latest WP/WC) plus one `floor` leg on the oldest supported WordPress + WooCommerce (WP 6.5 / WC 8.2); intermediate WP/WC versions are deliberately not tested. ## Architecture

### Namespaces and loading

All first-party PHP classes live under `Smart_Send\` and follow the [WordPress PHP standard](https://developer.wordpress.org/coding-standards/wordpress-coding-standards/php/): `Class_Name`, `snake_case()` methods and properties, and lowercase `class-*.php` filenames. The domain namespace replaces the historical class prefix; use `Smart_Send\Delivery\Pickup_Point`, for example. Keep acronym components uppercase (`API`, `REST_Controller`, `HTTP_Client`) and preserve signatures required by PHP or external interfaces, such as `JsonSerializable::jsonSerialize()`.

The entry file explicitly loads `includes/autoload.php` before accessing the composition root. Its single `spl_autoload_register()` callback handles the exact `Smart_Send\` prefix and uses three fixed roots, with the more specific prefixes first:

| Namespace prefix | Plugin directory |
|---|---|
| `Smart_Send\Admin\` | `admin/` |
| `Smart_Send\Frontend\` | `public/` |
| `Smart_Send\` | `includes/` |

After choosing the root, the loader maps namespace segments to lowercase directories with underscores replaced by hyphens, and the class to `class-*.php`. Thus `Smart_Send\Delivery\Pickup_Point` resolves to `includes/delivery/class-pickup-point.php`, and `Smart_Send\API\Exceptions\HTTP_Client_Exception` to `includes/api/exceptions/class-http-client-exception.php`. It ignores foreign classes, malformed names and missing files, allowing other autoloaders to run. New classes require only a correctly named file, never a per-class registry or directory scan.

The loader ships as source in the plugin ZIP. Shops need neither Composer nor a `vendor/` directory, and packaging has no PHP generation step. Composer remains development tooling. Keep all runtime classes loadable on PHP 7.4 and a case-sensitive filesystem, and load WooCommerce-dependent classes only after their parent/interface is available.

Namespace changes preserve wire payload field names, serialized data shapes, installed identifiers, hook strings and the global `SS_SHIPPING_WC()` accessor. The installed slug and text domain remain `smart-send-logistics`; use Smart Send names elsewhere. See the migration decision in [#195](https://github.com/smartsendio/woocommerce/issues/195) and the [release implementation plan](https://github.com/smartsendio/woocommerce/issues/172).

Single-entry WordPress plugin. `smart-send-logistics/smart-send-logistics.php` is a thin entry file: the plugin header, the `SS_SHIPPING_PLUGIN_FILE` constant, one `require`, the global `SS_SHIPPING_WC()` accessor and the bootstrap instantiation. The singleton `Smart_Send\Plugin` itself lives in `includes/class-plugin.php` and is the composition root: it constructs every feature component (typed properties) and wires their hooks. The `SS_SHIPPING_WC()` surface is deliberately small — component accessors (`settings()`, `order_meta()`, `method_resolver()`, `shipment_ids()`, `pickup_point_validator()`, `pickup_point_formatter()`, `pickup_point_lookup()`, `meta_box()`, `fulfillment_presenter()`, `fulfillment_controller()`, `fulfillment()`, `admin_notices()`, `bulk_actions()`, `test_connection()`, `rate_sorter()`), `get_api_handle()` (the memoized shared API client) and the bootstrap.

**Hook registration convention**: constructing a component has zero side effects - no `add_action`/`add_filter` calls in any constructor. Each component that owns hooks exposes an explicit `register_hooks(): void` method, and the composition root (`Smart_Send\Plugin::init()`, via `register_component_hooks()`) calls it once on every component in one clear pass, at the point the singleton already wires its own hooks (`init_hooks()`). The only hooks left directly on the singleton are genuinely plugin-lifecycle ones (`init`, textdomain, HPOS declaration, plugin-row links, `before_woocommerce_init`, the `woocommerce_shipping_methods` registration) - everything feature-specific lives on its owning component. Assets follow the same rule: each stylesheet/script is enqueued (with `SS_SHIPPING_VERSION`) by the component whose markup needs it, never blanket-enqueued from the bootstrap.

**Settings**: `Smart_Send\Support\Settings` (`includes/support/`) is the single typed reader of the plugin's global settings option — every checkbox-to-boolean normalization, missing-key default (including the documented v8 oddities, e.g. the logger's default-on debug gate) and option-key name (the `KEY_*` constants, shared with `Smart_Send\Shipping_Method\Method_Settings`' form definitions) exists exactly once. Components receive it at construction; nothing reads the raw settings array.

**Dependency timing**: `Smart_Send\Shipping_Method\Method` extends `WC_Shipping_Flat_Rate`, and `Smart_Send\Frontend\Block_Checkout` implements WooCommerce's Blocks `IntegrationInterface`. The composition root first verifies the supported WooCommerce version, then loads these integrations through the autoloader at their lifecycle entry points. Keep those guards when changing bootstrap code: WordPress can load this plugin before WooCommerce. Other components resolve through the same loader when constructed.

**Folder layout** (#140): `includes/` holds the composition root, the domain folders below and the API client under `includes/api/`. Exceptions live with the domain that owns them (`<domain>/exceptions/`, e.g. `booking/exceptions/`); only genuinely cross-domain exceptions (e.g. `Smart_Send\Exceptions\Not_Connected_Exception` — no API token configured) sit in the top-level `includes/exceptions/`. `admin/` and `public/` hold strictly the entry-point controllers + UI for their surface (plus `admin/css/`, `admin/js/`, `public/css/`). Each file contains one namespaced class; the same naming and loading rules apply to every domain and surface.

1. **Booking domain** in `includes/booking/` — the booking stage (#177): everything from "build the shipment" to "API response", and nothing that happens on the order afterwards. Booking receives the `WC_Order` (a booking always comes from an order) but never reads order meta or resolves shipping methods — that is fulfillment's job. One operation for both directions: `book( WC_Order, Smart_Send\Delivery\Delivery_Details, bool $is_return )`.
   - `Smart_Send\Booking\Order_Reader` — order → payload data extraction (receiver, item lines, totals, label freetext); the single reader of WC-native data. Item rows use `order_item_id` as allocation identity, with separate `product_id` and `variation_id`, and retain the saved order-line name, quantity and discounted amounts. `product_ids_for_item()` preserves stored references through WooCommerce's order-item metadata API when CRUD hydration rejects deleted IDs; `product_for_item()` also checks `exists()` so a deleted variation never turns into its surviving parent. Missing products expose translated `Deleted`, empty SKU, null weight/customs and `product_missing = true`; no historical reconstruction. Its filters (`smart_send_order_receiver`, `smart_send_receiver_phone`, `smart_send_payload_receiver`/`_items`/`_totals`, `smart_send_shipment_freetext` — the freetext printed on the label, deliberately not called "order note") stay in booking.
   - `Smart_Send\Booking\Shipment` — the request DTO: the internal shipment representation, a typed, WP-side value object (order/receiver/pickup-point/parcels/totals), zero WordPress dependencies; its parcels are typed `Smart_Send\Booking\Parcel` value objects.
   - `Smart_Send\Booking\Shipment_Builder` — `build( Smart_Send\Delivery\Delivery_Details )`: assembles the request DTO from `Smart_Send\Booking\Order_Reader`'s output plus the delivery details fulfillment decided on (method, pickup point, parcel plan resolved into typed `Smart_Send\Booking\Parcel` rows). No repository, no resolver; its one filter is `smart_send_parcel_default_weight( float, Smart_Send\Delivery\Parcel_Spec, WC_Order )` on the item-sum weight of a parcel whose spec declares no explicit weight (an explicit weight bypasses it; the implicit single parcel of an empty plan goes through it as a synthetic spec of every unit). Validates that every ordered unit is allocated exactly once; rejects missing/foreign line IDs, duplicate rows, invalid quantities and under/over-allocation. An empty plan or one itemless spec means all items in one parcel; multiple itemless specs require an itemless order. Emits one aggregated row per order line per parcel, with allocated quantities and proportionate net/tax amounts; cumulative currency rounding gives the final allocation the remainder. Parcel totals always equal allocated merchandise totals, including for an implicit or manually measured single parcel; order fees stay in shipment totals. Unknown item weights require a positive explicit parcel weight before the float default-weight filter runs. Throws `Smart_Send\Booking\Exceptions\Booking_Exception` with field errors for invalid allocations or unknown weights, and when the details carry no shipping method.
   - `Smart_Send\Booking\Booking_Service` — stateless (constructed with nothing, `WC_Order` passed per call): builds the request via the builder, runs `smart_send_booking_request( Smart_Send\Booking\Shipment, WC_Order, bool $is_return )`, hands it to `Smart_Send\API\Resources\Booking_Resource`, maps the API v1 response into the result DTO (`map_v1_response()` — the ONE place that knows the v1 response shape; the API v2 switch replaces it and nothing else), fires `smart_send_booking_completed( Smart_Send\Booking\Booked_Shipment, Smart_Send\Booking\Shipment, WC_Order )` and returns the DTO — or, on an API failure, fires `smart_send_booking_failed( Smart_Send\Booking\Exceptions\Booking_Exception, Smart_Send\Booking\Shipment, WC_Order )` and **throws** `Smart_Send\Booking\Exceptions\Booking_Exception` (in `booking/exceptions/`: the API exception as `previous`, `errors()` for validation field errors, `response_id()`). Errors are exceptions in booking, data in fulfillment. The same exception is what `Smart_Send\Delivery\Method_Resolver::resolve_return()` throws for a missing return method — the one deliberate delivery → booking reference, pinned by tests. `Smart_Send\Exceptions\Not_Connected_Exception` (no API token) stays separate. No raw response and no wire model ever leave this class.
   - `Smart_Send\Booking\Booked_Shipment` — the result DTO: the typed, serializable (`to_array()`/`from_array()`), WordPress-free result shaped for API v2 (smartsendio/dumbledore#2099) and populated from v1 today: shipment id, carrier, service code, return flag, state, booked-at, shipment-level tracking, `parcels()` of `Smart_Send\Booking\Booked_Parcel` (parcel id + tracking plus the `weight`/`length`/`width`/`height`/`reference` the parcel was booked with — the API echoes none of them back, so `map_v1_response()` correlates the response parcels with the request's `Smart_Send\Booking\Parcel`s **by index**, logging a `warning` and leaving the measures out when the counts differ), `documents()` of `Smart_Send\Booking\Shipment_Document` (type/format/layout/url plus the uploads copy as `local_path`/`local_url`) and `codes()` of `Smart_Send\Booking\Shipment_Code` (type/value/image/expiry/instructions). Outputs live on the shipment, never on a parcel; v1 yields exactly one `label`/`pdf` document and no codes. The inline v1 PDF bytes ride on the document as the non-serialized `inline_content` (excluded from `to_array()` and PHP serialization) — the v1 bridge until v2 provides a fetchable URL only.

2. **Fulfillment domain** in `includes/fulfillment/` — the fulfillment stage (#177): owns the WooCommerce order, decides *what* ships and *how*, calls booking, and writes the outcome onto the order. Two flows, because they genuinely differ (auto-return decision, tracking push and order status are outbound-only, different meta keys): `fulfill_outbound()` and `fulfill_return()` — do not collapse them into one method.
   - `Smart_Send\Fulfillment\Fulfillment_Service` — stateless; `fulfill_outbound( $order, bool $save_order_note = true, ?Smart_Send\Delivery\Delivery_Details $overrides = null, ?bool $with_return = null, ?Smart_Send\Delivery\Delivery_Details $return_overrides = null )` (`with_return` null → the method's `is_auto_return_enabled()`, true/false override it; the return leg runs only when the outbound *booking* succeeded, re-reads the freshly persisted details, retains the submitted outbound parcel plan in memory for both legs unless `$return_overrides` supplies a plan, and applies separate return method/pickup overrides — a submitted return method for the combined run of an order without a configured one, state B of #182) and `fulfill_return( $order, $save_order_note, $overrides )`. Per leg: resolves the delivery details (`resolve_delivery_details( WC_Order, bool $is_return, ?overrides )` — repository read + resolved method, the v8 return-pickup-point fallback, then the submitted overrides merged on top: a submitted field wins over the stored/derived one and a submitted method wins over the resolver, which is how an order without a Smart Send method (state B of #182) gets booked and how a submitted return method makes a missing configured one a non-failure; a pickup point submitted as a bare agent number (`Smart_Send\Delivery\Pickup_Point::is_agent_no_only()`) resolves to the stored point when the numbers match and otherwise through `Smart_Send\Delivery_Options\Pickup_Point_Lookup::find_by_agent_no()`, a miss failing the leg with a structured `agent_no` field error before any booking; public for Phase 7's "order id + details" queueing), applies `smart_send_delivery_details( Smart_Send\Delivery\Delivery_Details, WC_Order, bool $is_return )`, calls `Smart_Send\Booking\Booking_Service::book()`, catches `Smart_Send\Booking\Exceptions\Booking_Exception` and records it on the result as data (message, field errors, Response-ID, plus the merchant-facing HTML `format_booking_error()` renders here, not in booking), then — reading only the `Smart_Send\Booking\Booked_Shipment` — the side effects one step each: **step 0 persists the submitted overrides** through `Smart_Send\Delivery\Order_Meta::write()` (persist-after-success, #182: only after `book()` returned, before the shipment id; a failed booking leaves order meta byte-identical; only what has storage is written — the resolved pickup point or its clearing, the canonical parcel plan with order-item allocations — the method override and a spec's weight/dimensions are per booking and never stored; the booked DTO itself is still not persisted; the one new meta key is the booked-labels list written in the shipment-id step below), then, each with a filter: uploads copy of the documents (`smart_send_fulfillment_save_documents( bool, shipment, order )`, recorded on the document as `local_path`/`local_url`; a copy that cannot be saved is a *warning* on the entry with `steps.save_documents = 'failed'`, the shipment stays fulfilled and `download_url()` falls back to the API URL), shipment id meta (`Smart_Send\Fulfillment\Shipment_IDs::save_booked()`, no filter — the frozen per-direction id key *and* the append-only `_ss_shipping_labels` list the order screen's "Booked shipments" timeline renders, capped at `MAX_LABELS`; a failed booking appends nothing), order note (`smart_send_fulfillment_order_note( string $html, shipment, order )` — empty string adds none; the filtered note is what gets saved, its comment id lands on the result and the REST response renders it for the meta box to prepend), tracking push (`smart_send_fulfillment_tracking( bool, shipment, order )`, default outbound-only), status update (`smart_send_fulfillment_order_status( string|false, shipment, order )`, default the setting for outbound, `false` for return). Once the run is done and at least one shipment was fulfilled: `smart_send_order_fulfilled( WC_Order, Smart_Send\Fulfillment\Fulfillment_Result )`, once per run. Its HTML rendering (order note, `get_shipment_outputs_html()` for the bulk notice) iterates every document and every code — it never assumes one PDF. Called outside admin by Phase 7's async processing.
   - `Smart_Send\Fulfillment\Fulfillment_Result` — serializable run outcome, one entry per attempted leg, no exception object kept: `shipments()` / `get_outbound_shipment()` / `get_return_shipment()`, the per-shipment derivations (`get_order_note()`, `get_order_note_id()`, `get_steps()` — which side effects ran, `save_documents` being `true|false|'failed'`, `get_warnings()`), and the failures side by side (`get_outbound_error()` / `get_return_error()` as merchant HTML, `get_validation_errors()`, `get_error_details()` = `{message, response_id, fields, html}`); `to_array()` is the canonical JSON form (#182, the REST response's `shipments[]`: `direction`, `status`, `shipment` = `Smart_Send\Booking\Booked_Shipment::to_array()`, `steps`, `order_note {id, html}` — `html` null here, the presenter's `response()` renders it — `warnings`, or `error {message, response_id, fields, html}`); the historic AJAX shape (`to_legacy_response_array()`) is gone with the admin-ajax path. Holds no `WC_Order`.
   - `Smart_Send\Fulfillment\Shipment_IDs` — booked shipment id accessor; booking OUTCOMES, deliberately outside the delivery-details repository (`shipment_ids()`). `save()`/`save_booked()` write the frozen `META_LABEL_ID` / `META_RETURN_LABEL_ID` keys (the LATEST id per direction — a documented public contract, unchanged) and append a row `{ direction, shipment_id, booked_at (ISO 8601 UTC) }` to `Smart_Send\Delivery\Order_Meta::META_LABELS` (`_ss_shipping_labels`), read back by `labels()` oldest first and bounded by `MAX_LABELS` (50, newest kept). The new key is classified as a booking OUTCOME, so `Smart_Send\Support\Subscriptions_Compat` keeps it off renewal orders.

3. **Delivery-details domain** in `includes/delivery/` — what Smart Send knows about how an order ships (the data model; the checkout-facing services around it live in `includes/delivery-options/`):

## Logging policy

Two decoupled surfaces with distinct audiences — place every log/notice call deliberately on one of them (see issue #92):

1. **Checkout shipping debug bar** (`Smart_Send\Support\Checkout_Debug::add_notice()`) — for the merchant diagnosing checkout live (WooCommerce → Settings → Shipping → "Enable debug mode"). Carries the rate evaluation trace, which Smart Send rates ended up offered for the package, the overlapping-weight-row outcome, and pick-up point lookup results/failures. It never writes to the log — call `Smart_Send\Support\Logger` separately when a log entry is also wanted. Notices are a no-op during checkout AJAX (matching WooCommerce core), so the log entry is then the only trace.
2. **The WooCommerce log** (`Smart_Send\Support\Logger`, source `smart-send-logistics`) — an audit trail of business events (`info`) plus developer trace (`debug`).

| Level | Use for | Example |
|---|---|---|
| `info` | Business events a merchant/support agent cares about after the fact; always logged (ungated audit trail) | "Shipping label created", "Tracking number stored", "Pick-up point selected at checkout" |
| `debug` | Developer trace only, non-polluting — the ONLY level gated on the plugin "Debug Log" setting | "No Smart Send shipping method on order - skipping meta box content", rate evaluation detail, API request cycles (via `log_api_request`) |
| `warning` | Failures the plugin recovers from; always logged | "Pick-up point not found - agent number rejected" |
| `error` / `critical` | API and transport failures, and recoverable-but-abnormal states; always logged | "POST /shipments → 422 (312ms)" (via `log_api_request`), "Failed to load WooCommerce order when deleting pick-up point meta" |

Keep messages concise and greppable; put structured data (order id, agent no, shipment id, carrier) in the context array — the WooCommerce log viewer renders it natively.

## Existence-guard policy

`function_exists`/`class_exists` guards appear **only** where existence genuinely varies across the supported range (see issue #90). The three legitimate categories:

1. **Optional third-party plugins** — e.g. `wc_st_add_tracking_number` (Shipment Tracking), `WC_Subscriptions`.
2. **WP/WC APIs newer than our floors** (PHP 7.4 / WP 6.5 / WC 8.2) — none today: the WC 8.2 floor guarantees `FeaturesUtil`, the HPOS `CustomOrdersTableController` and the core Store API namespace, so those are called directly.
3. **Load-context differences** — e.g. `get_plugins()` outside admin (prefer `require_once` of the include over a silent guard).

Everything else — any WP or WC core API our floors guarantee — is called directly, with **no** guard: a guard on an impossible state silently swallows real bugs. Every kept guard carries a one-line comment naming why existence varies. The composition root in `includes/class-plugin.php` centralizes the WooCommerce 8.2 minimum check. Initialization, compatibility declarations and shipping-method registration all apply it before loading dependent integrations, since the latter two entry points can run before `init()`. `Requires Plugins: woocommerce` handles plugin presence on supported WordPress versions; it does not enforce a WooCommerce version. Everything downstream assumes the supported dependency is present.

Extension points are `smart_send_*` filters/actions, organised by the three stages `readme.txt`'s Developers section documents (every hook with its signature lives there — keep it in sync): **shipping methods at checkout** (rates via the WooCommerce-standard `woocommerce_shipping_smart_send_shipping_*` hooks, pickup points via `smart_send_pickup_point_search_params`, `smart_send_pickup_points_found`, `smart_send_pickup_point_option_label`, `smart_send_default_selected_pickup_point`, `smart_send_pickup_point_timeout`), **fulfillment** (`smart_send_delivery_details`, `smart_send_parcel_default_weight`, `smart_send_fulfillment_shipping_methods` — the methods the order screen's box offers, UI only, never an authorisation boundary —, the per-step `smart_send_fulfillment_save_documents` / `_order_note` / `_tracking` / `_order_status` filters, the `smart_send_order_fulfilled` action) and **booking** (the order reader's `smart_send_order_receiver`, `smart_send_receiver_phone`, `smart_send_payload_receiver`/`_items`/`_totals`, `smart_send_shipment_freetext`; the `smart_send_booking_request` filter and the `smart_send_booking_completed` / `smart_send_booking_failed` actions), plus connection/logging (`smart_send_api_endpoint`, `smart_send_sslverify`, `smart_send_logging`, `smart_send_configuration_url`, `smart_send_support_url`). Preserve these when refactoring — merchants rely on them via code snippets. **The stable contract passes typed value objects, never raw API request/response shapes** (#170, #177): fulfillment hooks pass `Smart_Send\Delivery\Delivery_Details` / `Smart_Send\Booking\Booked_Shipment` / `Smart_Send\Fulfillment\Fulfillment_Result` and the `WC_Order`, booking hooks pass `Smart_Send\Booking\Shipment` / `Smart_Send\Booking\Booked_Shipment` / `Smart_Send\Booking\Exceptions\Booking_Exception`, the pickup point filters pass `Smart_Send\Delivery\Pickup_Point[]`, and `smart_send_api_endpoint` carries the host only (the client appends `/api/v1/`) — so the 9.2 API v2 swap can ship as a minor. The `smart_send_payload_receiver`/`_items`/`_totals` filters on `Smart_Send\Booking\Order_Reader` pass plain arrays deliberately: they filter the plugin's own order-data extraction (keys owned by the reader, mapped to the wire shape later in the builder), not an API payload. Hooks that no longer exist in 9.0 (no aliases, no `do_action_deprecated`): `smart_send_shipping_label_created`, `smart_send_shipping_label_comment`, `smart_send_order_note`, `smart_send_tracking_url`, the pre-9.0 `smart_send_shipping_label_args`, `smart_send_order_pickup_point`, `smart_send_order_parcels`, `smart_send_parcel_weight`, `smart_send_payload_parcels` (#139), and the pre-release `smart_send_shipment_booked`. Rate meta keys `smart_send_shipping_method` / `smart_send_return_method` / `smart_send_auto_generate_return_label` and the settings field id `smart_send_shipping_order_status` share the prefix but are data keys, not hooks.

## Releasing

Releases go to the WordPress.org SVN repo, not GitHub. Use `sh bin/svn-deploy.sh` (interactive; copies `smart-send-logistics/` into an SVN checkout's trunk, tags, commits).

A version bump must update **three places in lockstep**:
- `smart-send-logistics/smart-send-logistics.php`: the `Version:` header
- `smart-send-logistics/includes/class-plugin.php`: the private `$version` property
- `smart-send-logistics/readme.txt`: the `Stable tag:`

Also add a changelog entry under `== Changelog ==` in `readme.txt` (WordPress.org readme format, not Keep a Changelog). When compatibility is verified against newer versions, bump `Tested up to:` / `WC tested up to:` in both files.
