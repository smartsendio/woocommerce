# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

The Smart Send WooCommerce plugin (display name "Smart Send", slug `smart-send-logistics` - the WordPress.org slug can never change). It adds Smart Send shipping methods to WooCommerce, shows carrier pick-up points at checkout, and generates shipping labels via the Smart Send API. Supported carriers: PostNord, GLS, DAO, Burd, Budbee, Bring.

The actual plugin lives entirely in `smart-send-logistics/` — that folder is what gets shipped to the WordPress.org plugin directory. The repo root only holds dev tooling (`composer.json` for phpcs, `bin/svn-deploy.sh`, README).

## Development environment

There is no PHP build step. Development is done against local WordPress + WooCommerce installs created by `bin/setup-local-dev.sh` (shorthand: `composer setup`; plugin symlinked in and activated). Two git-ignored env files at the repo root pin the store locations (`WP_PATH` relative to the repo root + `WP_URL`): `.env` is the persistent dev store (manual testing, demo mode; typically Herd-served at a `*.test` URL), `.env.testing` is the disposable testing store (default `./local-dev/wordpress` at `http://127.0.0.1:8181`, matching CI) that `bin/run-tests.sh` rebuilds from scratch on every `composer test:*` run. Explicit `--path`/`--url` flags and the legacy `WP_DEV_PATH`/`WP_BASE_URL` env vars override the files. The store is seeded to look like a real webshop (for manual testing and documentation screenshots): the vendored sample catalog in `sample-data/` (WooCommerce core sample products enriched to kg/cm and DKK, images committed for offline determinism — refresh via `bin/update-sample-data.sh`, never edit by hand), a Storefront homepage + primary menu, and default onboarding/marketing admin notices suppressed. The README.md has further details on the development environment.

### JS build

Two compiled assets: the checkout-block scripts (`src/pickup-point-block/` → `build/pickup-point-block/`) and the order screen meta box app (`src/order-fulfillment/` → `build/order-fulfillment/`, #182). Source lives in `src/` at the repo root (dev tooling, like `composer.json`); `npm run build` (`@wordpress/scripts`, Node version pinned in `.nvmrc`, config in `webpack.config.js`) compiles it into `smart-send-logistics/build/`, with `@woocommerce/dependency-extraction-webpack-plugin` turning `@wordpress/*`/`@woocommerce/*` imports into externals listed in generated `*.asset.php` files. The meta box app's files opt into the **classic JSX runtime** (`/** @jsxRuntime classic */ /** @jsx createElement */` pragmas + `createElement` from `@wordpress/element`): `@wordpress/scripts` defaults to the automatic runtime, whose `react-jsx-runtime` script handle WordPress registers only from 6.6, so on the 6.5 floor an automatic-runtime bundle silently never loads (#183) — keep the pragmas on every JSX file of that entry (an Integration test pins that `index.asset.php` lists no `react-jsx-runtime`). The `build/` output is **committed** — contributors without Node get a working plugin and `bin/svn-deploy.sh` stays copy-only — and `.github/workflows/js-build.yml` rebuilds on PRs touching `src/`/`package*.json`/`webpack.config.js` and fails if the committed output drifts from `src/`. After changing anything under `src/`, run `npm run build` and commit the result. Generated `build/` files are excluded from phpcs.

## Testing

Three Pest suites live in `tests/` (run on modern PHP; the plugin's PHP 5.6 floor only applies to `smart-send-logistics/` code):

- **Browser** (`tests/Browser`) — end-to-end Playwright tests against a *running* store over HTTP (`WP_BASE_URL`, default `http://127.0.0.1:8181`). Few and slow; cover the big flows. `tests/Browser/DevStoreTest.php` is the baseline health check of the dev store *itself* (Storefront theme active, store-page wiring, cart → checkout navigation, no JS errors) with no Smart Send seeding — when the store misbehaves, run that file first (`vendor/bin/pest tests/Browser/DevStoreTest.php`) before debugging the plugin.
- **Integration** (`tests/Integration`) — WordPress + WooCommerce loaded *in-process* by `tests/bootstrap.php` from the `bin/setup-local-dev.sh` install (override with `WP_DEV_PATH`); no web server needed. This is where scenario coverage lives (orders with coupons, discounts, fees → shipment payload, filters). Fixtures are built via the factories in `tests/Integration/Helpers.php`, which force-delete everything they create after each test — always create test data through them.
- **Docs** (`tests/Docs`) — *not* a correctness suite. Drives Playwright through real admin UI flows (same running store as Browser) and captures named screenshots for documentation, one test per meaningful UI state (see `tests/Docs/ShippingMethod/ConfigureShippingMethodTest.php` for the pattern — configuring a Smart Send shipping method on a zone, step by step; `tests/Docs/OrderFulfillment/OrderMetaBoxTest.php` captures the order meta box states of #182 into `docs/screenshots/OrderFulfillment/`, seeded through the Browser suite's `ss_browser_seed_store()` and API mock). Shared helpers live in `tests/Docs/Support/Screenshots.php`: `capture_doc_screenshot()` (asserts `assertNoJavaScriptErrors()` - not the stricter `assertNoSmoke()`, since WordPress admin always emits at least one benign console log - then saves under `docs/screenshots/<Area>/<name>.png`) and `highlight_element()` (spotlight-outlines the field a screenshot is calling out). Runs **headed** (a visible browser window) by default via `Playwright::headed()` in `tests/Pest.php` (a directory-level `tests/Docs/Pest.php` is never loaded by Pest for nested test files, so this lives at the root instead), so a developer regenerating screenshots locally can watch it work; falls back to headless when the `CI` env var is set (GitHub Actions sets this automatically) or when `SS_DOCS_HEADLESS` is set for a manual opt-out. To watch at human speed, set `SS_DOCS_SLOWMO=<ms>` (e.g. `SS_DOCS_SLOWMO=1500 composer test:docs`) — it pauses at every highlight/screenshot state via `docs_slowmo_pause()`; unset means full speed.

```bash
composer test:integration   # fresh testing store, then the Integration suite
composer test:browser       # fresh testing store + managed web server, then Browser
composer test:docs          # fresh testing store + managed web server; opens a visible browser locally
composer test               # Integration + Browser (not Docs - see below)
```

Every `composer test:*` script goes through `bin/run-tests.sh`: it **rebuilds the testing store (`.env.testing`) from scratch** (`bin/setup-local-dev.sh --env testing --force`) so runs never drift, and starts/stops the store's web server itself when `WP_URL` is a localhost URL. The order storage backend is a setup knob (`--order-storage hpos|posts|default`, or `WP_ORDER_STORAGE` in the env file): the Browser suite's order screen tests read `ss_browser_state()['hpos']` for paths and selectors, so the same files cover the HPOS and the legacy order screen — CI runs one HPOS-off leg (`--order-storage posts`) on the newest PHP next to the default matrix. For quick iteration against the *existing* testing store, call Pest directly (`vendor/bin/pest --testsuite=Integration`, etc.) — for Browser/Docs you then manage the server yourself.

For manual testing there is a demo mode (`composer demo:on` / `demo:off` / `demo:scenario -- <name>`, backed by `bin/demo-store.sh`): it applies the Browser suite's seeded store state + API mock to the local dev store and leaves it on until turned off. The mock and seeding sources are shared with the Browser suite (`tests/Browser/Support/ApiMockMuPlugin.php` + `Snippets/*.php`) — one source of truth; see README "Manual testing (demo mode)".

Local runs are fast: a direct `vendor/bin/pest` suite finishes in under 2 minutes, and a `composer test:*` run adds well under a minute of fresh-store provisioning on top (WP-CLI caches the downloads). If a run takes meaningfully longer, something is wrong (store not reachable, wrong `WP_URL`, a hung Playwright session) — kill it and investigate instead of waiting.

CI runs Integration and Browser (`.github/workflows/browser-tests.yml` and `integration-tests.yml`) on every pull request and on pushes to `main` and `develop`. Each matrix has `latest` legs (every supported PHP version — 7.4 to 8.5 for Browser, Pest's 8.3 to 8.5 for Integration — on the latest WP/WC) plus one `floor` leg on the oldest supported WordPress + WooCommerce (WP 6.5 / WC 8.2); intermediate WP/WC versions are deliberately not tested. A matrix leg with `canary: true` runs `continue-on-error` and must name the issue that makes it strict again (see README "CI" for the table and the php-fpm JIT note, #79). **Docs is intentionally not part of that PR-blocking path** — screenshot generation is slow and a broken screenshot doesn't mean broken code (assertions only guard against a broken/erroring page, not visual regressions). It runs on demand from `.github/workflows/docs-screenshots.yml` (`workflow_dispatch` only, headless, uploads `docs/screenshots/` as a build artifact rather than committing — a human reviews and commits the images after eyeballing them) and locally via `composer test:docs`. Screenshots are committed to `docs/screenshots/` at the repo root (outside `smart-send-logistics/`, mirroring the existing plugin-vs-dev-tooling split) since the whole point of the suite is producing images for direct use in documentation, same as `smartsendio/dumbledore`'s `tests/Docs/`. The Browser suite's API mock (`tests/Browser/Support/ApiMockMuPlugin.php`) also records every booking request it receives (`ss_browser_api_requests('booking')`, reset per test with `ss_browser_reset_api_requests()`) so a journey can assert what the plugin actually sent, e.g. the parcels of a split. **Docs is intentionally not part of that PR-blocking path** — screenshot generation is slow and a broken screenshot doesn't mean broken code (assertions only guard against a broken/erroring page, not visual regressions). **v9 refactoring rule: no refactor PR merges without tests covering the moved behaviour.** The characterization suites (payload golden tests, rate calculation, order meta, label generation, frontend display — see `tests/Integration`) capture current behaviour; a refactor PR must keep them green, and any code it moves that is not yet covered must gain tests in the same PR. ## Architecture

Single-entry WordPress plugin. `smart-send-logistics/smart-send-logistics.php` is a thin entry file (~55 lines): the plugin header, the `SS_SHIPPING_PLUGIN_FILE` constant, one `require`, the global `SS_SHIPPING_WC()` accessor and the bootstrap instantiation. The singleton `SS_Shipping_WC` itself lives in `includes/class-ss-shipping-wc.php` and is the composition root: it constructs every feature component (typed properties) and wires their hooks. The `SS_SHIPPING_WC()` surface is deliberately small — component accessors (`settings()`, `order_meta()`, `method_resolver()`, `shipment_ids()`, `pickup_point_validator()`, `pickup_point_formatter()`, `pickup_point_lookup()`, `meta_box()`, `fulfillment_presenter()`, `fulfillment_controller()`, `fulfillment()`, `admin_notices()`, `bulk_actions()`, `test_connection()`, `rate_sorter()`), `get_api_handle()` (the memoized shared API client) and the bootstrap.

**Hook registration convention**: constructing a component has zero side effects - no `add_action`/`add_filter` calls in any constructor. Each component that owns hooks exposes an explicit `register_hooks(): void` method, and the composition root (`SS_Shipping_WC::init()`, via `register_component_hooks()`) calls it once on every component in one clear pass, at the point the singleton already wires its own hooks (`init_hooks()`). The only hooks left directly on the singleton are genuinely plugin-lifecycle ones (`init`, textdomain, HPOS declaration, plugin-row links, `before_woocommerce_init`, the `woocommerce_shipping_methods` registration) - everything feature-specific lives on its owning component. Assets follow the same rule: each stylesheet/script is enqueued (with `SS_SHIPPING_VERSION`) by the component whose markup needs it, never blanket-enqueued from the bootstrap.

**Settings**: `SS_Shipping_Settings` (`includes/support/`) is the single typed reader of the plugin's global settings option — every checkbox-to-boolean normalization, missing-key default (including the documented v8 oddities, e.g. the logger's default-on debug gate) and option-key name (the `KEY_*` constants, shared with `SS_Shipping_Method_Settings`' form definitions) exists exactly once. Components receive it at construction; nothing reads the raw settings array.

**Loading**: there is no autoloader. `SS_Shipping_WC::includes()` loads every class file with explicit `require_once` calls (Composer cannot be assumed; the bespoke autoloader was removed in #43). The one exception is `SS_Shipping_WC_Method` itself: it extends `WC_Shipping_Flat_Rate` and this plugin loads before WooCommerce, so `include_shipping_method_class()` requires that one file lazily — from `init()` behind the bootstrap WooCommerce gate, and defensively from the `woocommerce_shipping_methods` filter callback. Its helper classes extend nothing and load eagerly like everything else. A new class file must be added to `includes()` (or, only for a WooCommerce-extending class, the lazy require).

**Folder layout** (#140): `includes/` holds the composition root, the domain folders below and the API client under `includes/lib/`. Exceptions live with the domain that owns them (`<domain>/exceptions/`, e.g. `booking/exceptions/`); only genuinely cross-domain exceptions (e.g. `SS_Shipping_Not_Connected_Exception` — no API token configured) sit in the top-level `includes/exceptions/`. `admin/` and `public/` hold strictly the entry-point controllers + UI for their surface (plus `admin/css/`, `admin/js/`, `public/css/`). WordPress-style classes keep the `SS_Shipping_*` prefix, no namespace, files named `class-ss-shipping-*.php`.

1. **Booking domain** in `includes/booking/` — the booking stage (#177): everything from "build the shipment" to "API response", and nothing that happens on the order afterwards. Booking receives the `WC_Order` (a booking always comes from an order) but never reads order meta or resolves shipping methods — that is fulfillment's job. One operation for both directions: `book( WC_Order, SS_Shipping_Delivery_Details, bool $is_return )`.
   - `SS_Shipping_Order_Reader` — order → payload data extraction (receiver, item lines, totals, label freetext); the single reader of WC-native data. Its filters (`smart_send_order_receiver`, `smart_send_receiver_phone`, `smart_send_payload_receiver`/`_items`/`_totals`, `smart_send_shipment_freetext` — the freetext printed on the label, deliberately not called "order note") stay in booking.
   - `SS_Shipping_Shipment` — the request DTO: the internal shipment representation, a typed, WP-side value object (order/receiver/pickup-point/parcels/totals), zero WordPress dependencies; its parcels are typed `SS_Shipping_Parcel` value objects.
   - `SS_Shipping_Shipment_Builder` — `build( SS_Shipping_Delivery_Details )`: assembles the request DTO from `SS_Shipping_Order_Reader`'s output plus the delivery details fulfillment decided on (method, pickup point, parcel plan resolved into typed `SS_Shipping_Parcel` rows). No repository, no resolver; its one filter is `smart_send_parcel_default_weight( float, SS_Shipping_Parcel_Spec, WC_Order )` on the item-sum weight of a parcel whose spec declares no explicit weight (an explicit weight bypasses it; the implicit single parcel of an empty plan goes through it as a synthetic spec of every unit). Throws `SS_Shipping_Booking_Exception` when the details carry no shipping method.
   - `SS_Shipping_Booking_Service` — stateless (constructed with nothing, `WC_Order` passed per call): builds the request via the builder, runs `smart_send_booking_request( SS_Shipping_Shipment, WC_Order, bool $is_return )`, hands it to `Smartsend\Resources\BookingResource`, maps the API v1 response into the result DTO (`map_v1_response()` — the ONE place that knows the v1 response shape; the API v2 switch replaces it and nothing else), fires `smart_send_booking_completed( SS_Shipping_Booked_Shipment, SS_Shipping_Shipment, WC_Order )` and returns the DTO — or, on an API failure, fires `smart_send_booking_failed( SS_Shipping_Booking_Exception, SS_Shipping_Shipment, WC_Order )` and **throws** `SS_Shipping_Booking_Exception` (in `booking/exceptions/`: the API exception as `previous`, `errors()` for validation field errors, `response_id()`). Errors are exceptions in booking, data in fulfillment. The same exception is what `SS_Shipping_Method_Resolver::resolve_return()` throws for a missing return method — the one deliberate delivery → booking reference, pinned by tests. `SS_Shipping_Not_Connected_Exception` (no API token) stays separate. No raw response and no wire model ever leave this class.
   - `SS_Shipping_Booked_Shipment` — the result DTO: the typed, serializable (`to_array()`/`from_array()`), WordPress-free result shaped for API v2 (smartsendio/dumbledore#2099) and populated from v1 today: shipment id, carrier, service code, return flag, state, booked-at, shipment-level tracking, `parcels()` of `SS_Shipping_Booked_Parcel` (parcel id + tracking), `documents()` of `SS_Shipping_Shipment_Document` (type/format/layout/url plus the uploads copy as `local_path`/`local_url`) and `codes()` of `SS_Shipping_Shipment_Code` (type/value/image/expiry/instructions). Outputs live on the shipment, never on a parcel; v1 yields exactly one `label`/`pdf` document and no codes. The inline v1 PDF bytes ride on the document as the non-serialized `inline_content` (excluded from `to_array()` and PHP serialization) — the v1 bridge until v2 provides a fetchable URL only.

2. **Fulfillment domain** in `includes/fulfillment/` — the fulfillment stage (#177): owns the WooCommerce order, decides *what* ships and *how*, calls booking, and writes the outcome onto the order. Two flows, because they genuinely differ (auto-return decision, tracking push and order status are outbound-only, different meta keys): `fulfill_outbound()` and `fulfill_return()` — do not collapse them into one method.
   - `SS_Shipping_Fulfillment_Service` — stateless; `fulfill_outbound( $order, bool $save_order_note = true, ?SS_Shipping_Delivery_Details $overrides = null, ?bool $with_return = null, ?SS_Shipping_Delivery_Details $return_overrides = null )` (`with_return` null → the method's `is_auto_return_enabled()`, true/false override it; the return leg runs only when the outbound *booking* succeeded, re-reads the freshly persisted details and takes only `$return_overrides` — a submitted return method for the combined run of an order without a configured one, state B of #182) and `fulfill_return( $order, $save_order_note, $overrides )`. Per leg: resolves the delivery details (`resolve_delivery_details( WC_Order, bool $is_return, ?overrides )` — repository read + resolved method, the v8 return-pickup-point fallback, then the submitted overrides merged on top: a submitted field wins over the stored/derived one and a submitted method wins over the resolver, which is how an order without a Smart Send method (state B of #182) gets booked and how a submitted return method makes a missing configured one a non-failure; a pickup point submitted as a bare agent number (`SS_Shipping_Pickup_Point::is_agent_no_only()`) resolves to the stored point when the numbers match and otherwise through `SS_Shipping_Pickup_Point_Lookup::find_by_agent_no()`, a miss failing the leg with a structured `agent_no` field error before any booking; public for Phase 7's "order id + details" queueing), applies `smart_send_delivery_details( SS_Shipping_Delivery_Details, WC_Order, bool $is_return )`, calls `SS_Shipping_Booking_Service::book()`, catches `SS_Shipping_Booking_Exception` and records it on the result as data (message, field errors, Response-ID, plus the merchant-facing HTML `format_booking_error()` renders here, not in booking), then — reading only the `SS_Shipping_Booked_Shipment` — the side effects one step each: **step 0 persists the submitted overrides** through `SS_Shipping_Order_Meta::write()` (persist-after-success, #182: only after `book()` returned, before the shipment id; a failed booking leaves order meta byte-identical; only what has storage is written — the resolved pickup point or its clearing, the parcel item rows — the method override and a spec's weight/dimensions are per booking and never stored; no new meta keys, the booked DTO is not persisted), then, each with a filter: uploads copy of the documents (`smart_send_fulfillment_save_documents( bool, shipment, order )`, recorded on the document as `local_path`/`local_url`; a copy that cannot be saved is a *warning* on the entry with `steps.save_documents = 'failed'`, the shipment stays fulfilled and `download_url()` falls back to the API URL), shipment id meta (`SS_Shipping_Shipment_Ids::save_booked()`, no filter), order note (`smart_send_fulfillment_order_note( string $html, shipment, order )` — empty string adds none; the filtered note is what gets saved, its comment id lands on the result and the REST response renders it for the meta box to prepend), tracking push (`smart_send_fulfillment_tracking( bool, shipment, order )`, default outbound-only), status update (`smart_send_fulfillment_order_status( string|false, shipment, order )`, default the setting for outbound, `false` for return). Once the run is done and at least one shipment was fulfilled: `smart_send_order_fulfilled( WC_Order, SS_Shipping_Fulfillment_Result )`, once per run. Its HTML rendering (order note, `get_shipment_outputs_html()` for the bulk notice) iterates every document and every code — it never assumes one PDF. Called outside admin by Phase 7's async processing.
   - `SS_Shipping_Fulfillment_Result` — serializable run outcome, one entry per attempted leg, no exception object kept: `shipments()` / `get_outbound_shipment()` / `get_return_shipment()`, the per-shipment derivations (`get_order_note()`, `get_order_note_id()`, `get_steps()` — which side effects ran, `save_documents` being `true|false|'failed'`, `get_warnings()`), and the failures side by side (`get_outbound_error()` / `get_return_error()` as merchant HTML, `get_validation_errors()`, `get_error_details()` = `{message, response_id, fields, html}`); `to_array()` is the canonical JSON form (#182, the REST response's `shipments[]`: `direction`, `status`, `shipment` = `SS_Shipping_Booked_Shipment::to_array()`, `steps`, `order_note {id, html}` — `html` null here, the presenter's `response()` renders it — `warnings`, or `error {message, response_id, fields, html}`); the historic AJAX shape (`to_legacy_response_array()`) is gone with the admin-ajax path. Holds no `WC_Order`.
   - `SS_Shipping_Shipment_Ids` — booked shipment id accessor; booking OUTCOMES, deliberately outside the delivery-details repository (`shipment_ids()`).

3. **Delivery-details domain** in `includes/delivery/` — what Smart Send knows about how an order ships (the data model; the checkout-facing services around it live in `includes/delivery-options/`):
   - The serializable value objects `SS_Shipping_Delivery_Details`, `SS_Shipping_Pickup_Point`, `SS_Shipping_Parcel_Plan`, `SS_Shipping_Parcel_Spec` — none holds a live `WC_Order`; Phase 7 queues these. All four have `to_array()`/`from_array()`, the canonical JSON shape of a fulfillment request (#182): `{shipping_method, pickup_point, parcel_plan {specs[] {reference, weight?, length?, width?, height?, items[] {id, quantity, name?}}}, addons}`, every field optional = "keep the stored/derived value"; `pickup_point` is a full point, a bare `{agent_no}` (resolved by the fulfillment service) or the `{clear: true}` sentinel (`clear_pickup_point()` / `is_pickup_point_cleared()` — needed because JSON null and absent are both "unspecified").
   - `SS_Shipping_Order_Meta` — the delivery-details repository, the SINGLE reader/writer of Smart-Send-owned order meta: `read()`/`write()` over `SS_Shipping_Delivery_Details` (a cleared pickup point deletes both pickup point keys; a parcel plan is stored as item rows only), frozen meta keys/formats, plus the META_* key classification (`order_meta()`). `write()` flags itself via `is_writing()` so the Custom Fields validator's legacy-storage meta hooks (which WooCommerce's by-mid meta updates trigger on every `save()`) do not re-validate a programmatic write.
   - `SS_Shipping_Method_Resolver` — shipping method resolution from the order's shipping items: `resolve_outbound()`/`resolve_return()`, auto-return flag, the v8 return-pickup-point fallback (`method_resolver()`).

4. **Delivery-options surface** in `includes/delivery-options/` — the checkout/admin-facing services around delivery options (today that is pickup point selection; future options like delivery time windows join here). They consume the delivery data model; kept in `includes/` rather than `public/` because the validator and formatter also serve admin surfaces:
   - `SS_Shipping_Checkout_Options` — decides which delivery-option sections the checkout renders for a shipping method and owns the pickup point section's status vocabulary (`PICKUP_POINT_STATUS_*` + customer-facing text), shared by the classic and block checkouts so the two surfaces cannot drift apart.
   - `SS_Shipping_Pickup_Point_Formatter` — the single place a pickup point becomes display text: checkout drop-down labels, order-details block, meta box block, settings option labels (`pickup_point_formatter()`).
   - `SS_Shipping_Pickup_Point_Lookup` — headless closest-pickup-points lookup: API call, lookup filters, failure reporting, session cache; the seam Phase 6's Checkout Block support builds on (`pickup_point_lookup()`). It maps the raw API objects into `SS_Shipping_Pickup_Point` value objects at the API boundary, before the `smart_send_pickup_points_found` filter and the session cache (which stores the plain `to_object()` form, never class instances), so every consumer downstream sees the DTO only (#170).
     Its `find_by_agent_no( string $carrier, string $country, string $agent_no ): SS_Shipping_Pickup_Point` is the shared "resolve an entered agent number" API call (#182), throwing `SS_Shipping_Pickup_Point_Not_Found_Exception` (`delivery-options/exceptions/`) on a miss; the validator, the fulfillment service's pickup point override, the Store API checkout's session-cache-miss fallback and the meta box's REST lookup route all go through it.
   - `SS_Shipping_Pickup_Point_Validator` — agent-number validation on the order screen's Custom Fields box, covering both legacy meta hooks and the HPOS edit seams (`pickup_point_validator()`); the API call itself is the lookup's `find_by_agent_no()`, the hooks, messages and stored-object format are unchanged.
   - `SS_Shipping_Store_Api` — the Checkout Block's Store API twin (see Frontend below): cart extension data down, checkout `agent_no` persistence + session update callback up.

5. **Shipping-method layer** in `includes/shipping-method/`:
   - `SS_Shipping_WC_Method` — the shipping method, extends `WC_Shipping_Flat_Rate` (the one lazily-loaded file); rate calculation (`calculate_shipping`, `is_available`, `is_free_shipping`). WooCommerce's settings framework dispatches `validate_*_field`/`generate_*_html` on this instance, so it keeps thin wrappers that delegate to its components: `SS_Shipping_Method_Settings` (form field definitions + validation), `SS_Shipping_Method_Form_Renderer` (custom field type rendering), `SS_Shipping_Method_Catalog` (per-carrier method lists and code→name lookup), `SS_Shipping_Availability_Reporter` (the data-driven shipping-class/free-shipping outcome messages for log + checkout debug bar).
   - `SS_Shipping_Method_Code` — a method code (e.g. `postnord_agent`) as a value object: `carrier()`/`type()` parsing plus the catalog-backed `name()` lookup.

Naming convention follows this same split: `SS_Shipping_*` (WordPress-style) code uses snake_case methods; the `Smartsend\` PSR-style lib uses camelCase — a call chain crossing the boundary (e.g. `SS_SHIPPING_WC()->get_api_handle()->bookings()->findByAgentNo()`) is expected to mix both, not a bug to fix.

## Logging policy

Two decoupled surfaces with distinct audiences — place every log/notice call deliberately on one of them (see issue #92):

1. **Checkout shipping debug bar** (`SS_Shipping_Checkout_Debug::add_notice()`) — for the merchant diagnosing checkout live (WooCommerce → Settings → Shipping → "Enable debug mode"). Carries the rate evaluation trace, which Smart Send rates ended up offered for the package, the overlapping-weight-row outcome, and pick-up point lookup results/failures. It never writes to the log — call `SS_Shipping_Logger` separately when a log entry is also wanted. Notices are a no-op during checkout AJAX (matching WooCommerce core), so the log entry is then the only trace.
2. **The WooCommerce log** (`SS_Shipping_Logger`, source `smart-send-logistics`) — an audit trail of business events (`info`) plus developer trace (`debug`).

| Level | Use for | Example |
|---|---|---|
| `info` | Business events a merchant/support agent cares about after the fact; always logged (ungated audit trail) | "Shipping label created", "Tracking number stored", "Pick-up point selected at checkout" |
| `debug` | Developer trace only, non-polluting — the ONLY level gated on the plugin "Debug Log" setting | "No Smart Send shipping method on order - skipping meta box content", rate evaluation detail, API request cycles (via `log_api_request`) |
| `warning` | Failures the plugin recovers from; always logged | "Pick-up point not found - agent number rejected" |
| `error` / `critical` | API and transport failures, and recoverable-but-abnormal states; always logged | "POST /shipments → 422 (312ms)" (via `log_api_request`), "Failed to load WooCommerce order when deleting pick-up point meta" |

Keep messages concise and greppable; put structured data (order id, agent no, shipment id, carrier) in the context array — the WooCommerce log viewer renders it natively.

## Existence-guard policy

`function_exists`/`class_exists` guards appear **only** where existence genuinely varies across the supported range (see issue #90). The three legitimate categories:

1. **Optional third-party plugins** — e.g. `wc_st_add_tracking_number` (Shipment Tracking), `WC_Subscriptions`.
2. **WP/WC APIs newer than our floors** (PHP 7.4 / WP 6.5 / WC 8.2) — none today: the WC 8.2 floor guarantees `FeaturesUtil`, the HPOS `CustomOrdersTableController` and the core Store API namespace, so those are called directly.
3. **Load-context differences** — e.g. `get_plugins()` outside admin (prefer `require_once` of the include over a silent guard).

Everything else — any WP or WC core API our floors guarantee — is called directly, with **no** guard: a guard on an impossible state silently swallows real bugs. Every kept guard carries a one-line comment naming why existence varies. Exactly one bootstrap-level WooCommerce-active check lives in `smart-send-logistics.php` (`init()`'s `WOOCOMMERCE_VERSION` gate — belt-and-braces for WP < 6.5, where `Requires Plugins: woocommerce` is not enforced); everything downstream assumes WooCommerce is present.

Extension points are `smart_send_*` filters/actions, organised by the three stages `readme.txt`'s Developers section documents (every hook with its signature lives there — keep it in sync): **shipping methods at checkout** (rates via the WooCommerce-standard `woocommerce_shipping_smart_send_shipping_*` hooks, pickup points via `smart_send_pickup_point_search_params`, `smart_send_pickup_points_found`, `smart_send_pickup_point_option_label`, `smart_send_default_selected_pickup_point`, `smart_send_pickup_point_timeout`), **fulfillment** (`smart_send_delivery_details`, `smart_send_parcel_default_weight`, the per-step `smart_send_fulfillment_save_documents` / `_order_note` / `_tracking` / `_order_status` filters, the `smart_send_order_fulfilled` action) and **booking** (the order reader's `smart_send_order_receiver`, `smart_send_receiver_phone`, `smart_send_payload_receiver`/`_items`/`_totals`, `smart_send_shipment_freetext`; the `smart_send_booking_request` filter and the `smart_send_booking_completed` / `smart_send_booking_failed` actions), plus connection/logging (`smart_send_api_endpoint`, `smart_send_sslverify`, `smart_send_logging`, `smart_send_configuration_url`, `smart_send_support_url`). Preserve these when refactoring — merchants rely on them via code snippets. **The stable contract passes typed value objects, never raw API request/response shapes** (#170, #177): fulfillment hooks pass `SS_Shipping_Delivery_Details` / `SS_Shipping_Booked_Shipment` / `SS_Shipping_Fulfillment_Result` and the `WC_Order`, booking hooks pass `SS_Shipping_Shipment` / `SS_Shipping_Booked_Shipment` / `SS_Shipping_Booking_Exception`, the pickup point filters pass `SS_Shipping_Pickup_Point[]`, and `smart_send_api_endpoint` carries the host only (the client appends `/api/v1/`) — so the 9.2 API v2 swap can ship as a minor. The `smart_send_payload_receiver`/`_items`/`_totals` filters on `SS_Shipping_Order_Reader` pass plain arrays deliberately: they filter the plugin's own order-data extraction (keys owned by the reader, mapped to the wire shape later in the builder), not an API payload. Hooks that no longer exist in 9.0 (no aliases, no `do_action_deprecated`): `smart_send_shipping_label_created`, `smart_send_shipping_label_comment`, `smart_send_order_note`, `smart_send_tracking_url`, the pre-9.0 `smart_send_shipping_label_args`, `smart_send_order_pickup_point`, `smart_send_order_parcels`, `smart_send_parcel_weight`, `smart_send_payload_parcels` (#139), and the pre-release `smart_send_shipment_booked`. Rate meta keys `smart_send_shipping_method` / `smart_send_return_method` / `smart_send_auto_generate_return_label` and the settings field id `smart_send_shipping_order_status` share the prefix but are data keys, not hooks.

## Releasing

Releases go to the WordPress.org SVN repo, not GitHub. Use `sh bin/svn-deploy.sh` (interactive; copies `smart-send-logistics/` into an SVN checkout's trunk, tags, commits).

A version bump must update **three places in lockstep**:
- `smart-send-logistics/smart-send-logistics.php`: the `Version:` header
- `smart-send-logistics/includes/class-ss-shipping-wc.php`: the private `$version` property
- `smart-send-logistics/readme.txt`: the `Stable tag:`

Also add a changelog entry under `== Changelog ==` in `readme.txt` (WordPress.org readme format, not Keep a Changelog). When compatibility is verified against newer versions, bump `Tested up to:` / `WC tested up to:` in both files.
